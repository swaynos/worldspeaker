# R01-ABIL-01-QA-003 — ability-result semantic coherence

## Finding

Structural JSON Schema validation accepted contradictory logical results, including
`executed` lightning results whose envelope and facts disagreed on `actionId` or
`executedAt`, and `failed`/`unknown` results with `reasonCode: none` and no facts.
The former success-shaped output was therefore not internally coherent even though
each individual field passed its local schema.

## Change and reusable API

`abilityResultSemanticsAreCoherent(value)` in
`companion/src/ability-catalogue.ts` is the pure cross-field predicate. The result
schema calls it after checking local field types, bounds, enums, and closed-object
shapes. The predicate does not consult a server, a world, a provider, or an action
journal. It checks only whether the supplied result is internally consistent.

The result-state/reason compatibility table implemented by the predicate is:

| State | Allowed reason codes |
| --- | --- |
| `rejected` | `invalid_input`, `unsupported_contract`, `unsupported_state`, `permission_denied`, `target_unavailable`, `out_of_scope`, `protected_area`, `stale_context`, `rate_limited`, `concurrency_limited`, `storage_unavailable`, `execution_unavailable` |
| `admitted`, `submitted`, `executed` | `none` |
| `failed` | `unsupported_state`, `permission_denied`, `target_unavailable`, `out_of_scope`, `protected_area`, `stale_context`, `storage_unavailable`, `execution_unavailable`, `execution_failed` |
| `partial` | `unsupported_state`, `permission_denied`, `target_unavailable`, `out_of_scope`, `protected_area`, `stale_context`, `deadline_expired`, `cancelled`, `storage_unavailable`, `execution_unavailable`, `execution_failed`, `outcome_unknown` |
| `expired` | `deadline_expired` |
| `cancelled` | `cancelled` |
| `unknown` | `outcome_unknown`, `storage_unavailable` |

`retryAfterMs` is otherwise null. A non-null value is accepted only for a rejected
`rate_limited` result, as a known cooldown/rate hint in the schema's inclusive
0–30,000 ms range; it is not permission to retry. `concurrency_limited` does not
establish a cooldown time.

## Facts, time, and step coherence

- A query has a complete `ObserveFacts` snapshot only when `state` is `executed`
  and `reasonCode` is `none`. The envelope `observedAt` must exactly equal the
  snapshot's `observedAt`; query `executedAt` is null. Other query outcomes have
  null facts and null observation/execution times. A query is never `partial`.
- Effect `executed` and `partial` outcomes require lightning facts. No facts means
  both envelope times are null. Lightning `observedAt` is null, and envelope
  `actionId`/`executedAt` must exactly equal the copies in its facts. The action's
  execution time can remain null if it is not known.
- Lightning steps are ordered: presentation first, then at most one damage step.
  `visualOnly: true` has only a presentation step. In damage mode, confirmed
  presentation is followed by one recorded damage step; any damage step is
  ordered after (never before) presentation. A later confirmed damage step does
  not erase an earlier failed/unknown presentation. Any confirmed effect requires
  resolved coordinates. Confirmed damage carries measured numeric values and a
  disposition; unconfirmed damage carries null numeric/disposition fields.
  `applied` requires positive measured loss; `invulnerable` and `protection_veto`
  require zero loss. `non_lethal_limit` can report positive measured loss below
  the contract ceiling. Mitigated zero damage remains valid.
- `executed` lightning has only confirmed steps. `failed` facts, if present, have
  no confirmed or unknown step. `unknown` may have null facts, or facts with an
  unknown step and no confirmed step. `partial` requires a known confirmed step
  and a distinct non-confirmed step. Thus confirmed presentation followed by
  failed, unknown, or prevented damage stays a truthful `partial` result; it is
  neither rejected nor rewritten as total failure or rollback.
- Steps have no target/world/dimension authority fields. The standalone target
  and dimension facts are not compared to request IDs, world-instance IDs, or
  other unrelated envelope fields: a dimension identifier is not a world ID,
  and this result validator cannot bind a result to a submitted request's target.
  Only literally duplicated fields are compared.

## Authority and uncertainty boundary

This validation is not execution authority and does not establish that any
reported world fact is true. It cannot authorize a target, prove a mutation,
confirm public presentation, infer player receipt, roll back a partial effect,
or resolve an unknown outcome. Facts in the shared semantic corpus are synthetic
shape/coherence fixtures, not authoritative world-execution evidence. The future
Java result DTO/predicate should mirror this table and these rules; it is outside
this change.

## Verification

The shared positive corpus covers all nine states and all reason codes. One-field
negative mutations cover reason/state contradictions, duplicated identity/time
mismatches, unsupported retry hints, partial/unknown handling, step order/count,
damage-mode evidence, confirmed damage dispositions, and attempts to smuggle
target/world fields into steps.

Focused TypeScript typecheck/build and runtime verification passed. The package
prebuild check reported canonical ability metadata in sync.

```text
npm run typecheck
npm run build
node --test dist/test/ability-result-semantics.test.js
pass 5, fail 0
```

This is focused companion verification only. Final cross-builder QA remains a
parent-session check.
