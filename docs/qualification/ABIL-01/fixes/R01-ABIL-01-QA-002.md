# R01-ABIL-01-QA-002 — exact ability result numbers

## Finding

Two lossy conversions were accepted on ability-result ingress. A positive health
token such as `1e-50` rounded to binary32 zero and passed the non-negative check.
An `observedAt` token such as `1.0000000000000001` rounded to JavaScript `1`,
then passed as an integer even though the source decimal was fractional. The old
float check also accepted arbitrary double values merely because `Math.fround`
could round them to some finite float.

## Shared number policy

The initial Java-only F-02 iteration and interim report incorrectly rejected
Node's `JSON.stringify(Math.fround(0.1))` value
`0.10000000149011612`. That is the exact binary64 rendering of the same binary32
value represented by Java's `0.1`; rejecting it was a cross-runtime parity bug.
That Java-only policy is superseded by the dual-encoding policy below.

The shared policy accepts a raw decimal only when its exact mathematical value
equals either Java `Float.toString(f)` or ECMAScript
`JSON.stringify(Math.fround(f))` for the same finite binary32 `f`. The raw token
is compared before `Number` parsing, so an added tail such as
`0.100000001490116120000000000001` cannot masquerade as Node's canonical
`0.10000000149011612` merely because both parse to the same JavaScript number.
Both accepted forms normalize to the single `Math.fround` value in the strict
JSON result path.

`normalizeFloat32WireNumber(value)` returns that normalized binary32 value or
null. The historical names `isJavaFloat32WireNumber` and
`isCanonicalJavaFloat32JsonNumberToken` remain for API stability, but both now
cover Java and ECMAScript canonical forms. The `worldspeakerFloat32` predicate
uses the value-level API; `parseStrictJson` uses the exact-token API and then
returns normalized float32 values. This is **normalization, not clamping**: no
health, max-health, or damage value is capped or rewritten to a bound. The
existing health-at-most-max semantic remains authoritative and no fixed health
ceiling is added.

- For bits `0x3dcccccd` (`0.1f`), Java emits `0.1`; Node emits
  `0.10000000149011612`. Both are accepted and normalize to
  `Math.fround(0.1)`.
- For minimum-subnormal bits `0x00000001`, Java emits `1.4E-45`; Node emits
  `1.401298464324817e-45`. For `Float.MAX_VALUE` bits `0x7f7fffff`, Java emits
  `3.4028235E38`; Node emits `3.4028234663852886e38`. Each pair is accepted and
  normalizes to the same binary32 value.
- Nonzero-to-zero underflow (`1e-50`), overflow to infinity, noncanonical
  in-range rounding, and hidden extra decimal precision are rejected. True
  subnormals and `Float.MAX_VALUE` are preserved; no value-specific blacklist is
  used. Float bounds remain separate, so negative canonical numbers still fail
  nonnegative health/damage bounds.
- Java `Float.toString(-0.0f)` emits `-0.0` and retains negative zero through
  parsing. ECMAScript `JSON.stringify(Math.fround(-0))` emits `0`, which parses
  as positive zero; JSON has already lost the sign, so that Node encoding cannot
  preserve negative zero. Both remain mathematical zero for nonnegative bounds.

## Raw integer tokens and result ingress

`parseStrictJson` checks original number tokens before returning parsed values,
then normalizes the accepted float32 fields to their binary32 value.
The non-negative safe-integer field set includes `contractVersion`,
`policyRevision`, `observedAt`, `executedAt`, `retryAfterMs`, and the existing
schema/policy/wall-clock revision fields. Coordinates inherit an exact signed
safe-integer token check through nested arrays; their domain/world bounds remain
the responsibility of the existing coordinate schema predicate. Decimal and
exponent spellings are accepted only when their exact mathematical value is an
integer in range. Negative zero is accepted where the schema's nonnegative bound
allows zero; fractional values that merely round to an integer are not.

`validateAbilityResultBytes` uses this same strict parser, with the existing
whole-frame 4 KiB bound and nesting depth of eight, before schema validation.
Thus result fields not present in an ability dialogue request receive the same
raw-token checks. No result DTO or health semantic was moved into the parser.

## Shared API for Java F05

The TypeScript token API in `companion/src/protocol-text.ts` defines the reusable
contract:

- `isSafeJsonIntegerToken(token)` — exact signed mathematical safe integer,
  including negative zero; use for raw coordinate elements before converting
  them to a JavaScript/Java numeric type.
- `isNonNegativeSafeJsonIntegerToken(token)` — same exact test plus nonnegative
  mathematical value for timestamps, revisions, and retry values.
- `isCanonicalJavaFloat32JsonNumberToken(token)` — exact raw decimal check for
  either canonical Java or ECMAScript binary32 serialization (historical API
  name; both forms are accepted).
- `normalizeFloat32WireNumber(value)` — returns the normalized binary32 value
  for either canonical form, or null; this is the reusable cross-runtime
  normalization API for F-05.
- `isJavaFloat32WireNumber(value)` — value-level predicate where no raw JSON
  token is available (historical API name; both forms are accepted).

Coordinate integer precision is separate from coordinate domain validation:
the later Java validator should first preserve/check the raw signed safe integer,
then apply the already-selected Minecraft block-position bounds. This change does
not alter that coordinate domain. The Java result validator/DTO remains future
work.

## Shared corpus

`compatibility/ability-numbers-v1-corpus.json` stores actual
`Float.toString(float)` outputs from OpenJDK 21.0.3+9 and actual
`JSON.stringify(Math.fround(value))` output from Node 24.22.1 for each same raw
binary32 bit pattern. It includes positive and negative zero, minimum/maximum
subnormals, minimum normal, `Float.MAX_VALUE`, powers and mantissa cases, health
above 20, and 32 finite raw-bit samples from seed `0x5eedc0de`. It also records
hidden-precision, underflow, overflow, negative-bound, and exact integer-token
cases for the later Java validator.

The shared corpus checks both actual encoder outputs for every listed raw bit
pattern and verifies they normalize identically, except that Node's JSON `0`
cannot retain the negative-zero sign. Representative Java/Node pairs are
`0x00000001`: `1.4E-45` / `1.401298464324817e-45`;
`0x00800000`: `1.1754944E-38` / `1.1754943508222875e-38`;
`0x7f7fffff`: `3.4028235E38` / `3.4028234663852886e38`; and
`0x3dcccccd`: `0.1` / `0.10000000149011612`.

## Verification

Focused TypeScript tests exercise the corpus through both shared predicates and
the production result-byte path. With the supplied Node 24.22.1 runtime, the
companion TypeScript typecheck passed, and the focused `ability-numbers` plus
`strict-json` tests passed (9/9). The result-extension regression test also
passed independently. Separately invoked broader test files failed before their
assertions because existing corpus fixture paths resolved outside the repository;
no parser-focused test failed. Final cross-builder typecheck/test gates remain the
parent-session QA responsibility.
